# Pavliuk-Tech Inventory

Невеликий застосунок для обліку комп'ютерного обладнання в магазині Pavliuk-Tech.
Це лабораторна робота 1 (Cloud Services, осінь 2026): застосунок запакований у Docker,
розгорнутий в AWS через Terraform і оновлюється автоматично через GitHub Actions.

Документація API (Swagger): та сама адреса + `/docs`

## Що він вміє

- ведення категорій обладнання (ноутбуки, відеокарти, монітори тощо);
- ведення товарів: артикул, назва, бренд, ціна, кількість на складі;
- рухи складу: надходження, продаж, коригування, з історією;
- проста веб-сторінка на `/`, де все це можна робити мишкою.

Кількість товару змінюється тільки через рухи складу, тому завжди видно, звідки взялась кожна цифра.

## З чого зроблено

FastAPI (Python 3.15), PostgreSQL 16, SQLAlchemy, звичайні HTML/CSS/JS без фреймворків.
Docker для пакування, Terraform для інфраструктури, AWS (ECS Fargate, RDS, ALB, ECR),
GitHub Actions для автоматичного деплою.

## Структура проєкту

```
app/
  main.py        ендпоінти API і маршрут сторінки
  models.py      таблиці бази даних
  schemas.py     перевірка даних, що приходять і йдуть через API
  database.py    підключення до бази (адреса береться зі змінної DATABASE_URL)
  static/        сторінка: index.html, style.css, app.js
terraform/       уся інфраструктура AWS
.github/workflows/deploy.yml   автоматичний деплой
Dockerfile       збірка образу
compose.yaml     локальний запуск: застосунок + PostgreSQL
.env.example     приклад змінних для локального запуску
```

## Запуск на своєму комп'ютері

```bash
cp .env.example .env
docker compose up --build
```

Після запуску:
- сторінка: http://localhost:8000
- Swagger: http://localhost:8000/docs

Файл `.env` у репозиторій не потрапляє, там лежать паролі до локальної бази.
Дані бази зберігаються в volume `pgdata`:

```bash
docker compose down       # зупинити, дані лишаються
docker compose up         # запустити знову, дані на місці
```

Подивитися, що лежить у базі:

```bash
docker compose exec db psql -U pavliuk -d pavliuk_tech -c "SELECT * FROM products;"
```

## База даних

Три таблиці:

- `categories`: назва категорії, унікальна;
- `products`: товари. Артикул унікальний, ціна більша за нуль, кількість не менша за нуль,
  кожен товар належить категорії (категорію, у якій є товари, видалити не можна);
- `stock_movements`: історія змін складу (надходження, продаж, коригування).
  При видаленні товару його історія видаляється разом з ним.

Таблиці створюються самі при першому запуску застосунку.

## API

| Метод | Адреса | Що робить |
|---|---|---|
| GET | `/health` | перевірка, що застосунок живий (її використовує балансувальник) |
| GET | `/health/db` | перевірка зв'язку з базою |
| GET, POST | `/categories` | список категорій, створення |
| PUT, DELETE | `/categories/{id}` | перейменування, видалення |
| GET, POST | `/products` | список (фільтри `category_id`, `q`, `limit`, `offset`), створення |
| GET, PUT, DELETE | `/products/{id}` | один товар, зміна, видалення |
| GET, POST | `/products/{id}/movements` | історія складу, нове надходження чи продаж |

## Розгортання в AWS

1. У файлі `terraform/github_oidc.tf` на початку вказано, якому репозиторію GitHub
   дозволено розгортати.
2. Створити інфраструктуру:
   ```bash
   cd terraform
   terraform init
   terraform apply
   ```
3. Адреса застосунку: `terraform output app_url`.

Що саме створюється:

- мережа (VPC) з двома публічними і двома приватними підмережами;
- балансувальник ALB у публічних підмережах: тільки він доступний з інтернету;
- застосунок (ECS Fargate) у приватних підмережах, приймає трафік тільки від балансувальника;
- база PostgreSQL (RDS) у приватних підмережах, без публічної адреси,
  приймає підключення тільки від застосунку;
- реєстр образів ECR;
- NAT-gateway.

Пароль до бази Terraform генерує сам і зберігає в SSM Parameter Store.
Звідти ECS підставляє його в контейнер як змінну `DATABASE_URL`, у коді і репозиторії його немає.

## Автоматичний деплой

Кожен `git push` у `main` запускає `.github/workflows/deploy.yml`:

1. GitHub входить в AWS через OIDC, без збережених ключів доступу
   (роль приймає запити тільки від цього репозиторію і тільки з гілки `main`);
2. збирається Docker-образ і публікується в ECR з тегом, що дорівнює хешу коміту;
3. у ECS реєструється нова версія завдання з цим образом;
4. сервіс оновлюється, нові контейнери перевіряє балансувальник, і лише потім зупиняються старі.
